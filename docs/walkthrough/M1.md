# M1 walkthrough: canonical model and parsing

## What was built
`packages/core` can now read a rooming list. `parseRoomingList(bytes, options)` takes a CSV or Excel file and returns three things: the guests as entries, every problem it found as issues, and how each column was understood. It does not care what the file is called. The first bytes decide whether it is Excel, and the text decides whether it is a CSV with commas, semicolons or tabs. Headers like `Check-In`, `# Adults` or `Guest Name` are matched to fields through an alias table. Dates in ISO, `11/10/2026` or `10 Nov 2026` form become plain `YYYY-MM-DD` strings. A bad cell never stops the run: it adds an issue that names the row and says how to fix it, and parsing continues. Only file-level problems (empty file, missing columns, too many rows) stop early.

## Design decisions
1. **Dates are strings, never `Date` objects.** A hotel night is a calendar day, not a moment in time. All date arithmetic lives in `plain-date.ts`, which uses `Date` only at UTC midnight, so a server in another time zone can't shift a stay by a day. The one other place a `Date` appears is the Excel reader, which turns a date cell straight into a string.
2. **Two entry types.** `RoomingEntry` is the strict shape the hotel files need. `ParsedEntry` lets the last name and dates be missing, because a planner's file often has gaps. The validator (M2) reports those gaps instead of the parser silently dropping rows.
3. **One rule table.** `src/issues.ts` holds the code and severity of every rule ID. The parser, validator and exporters all use it, so they can't disagree.
