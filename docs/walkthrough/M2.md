# M2 walkthrough: validation rules and summary

## What was built
`validateRoomingList(list, { entryRows })` checks a parsed rooming list against the rules a hotel cares about. Is the departure after the arrival? Does the stay fit the block dates, including shoulder days? Is the room type one the block holds? Does every sharer point at a real primary? Do too many people share one room? Is the same guest listed twice? Each rule is one small exported function in `validate/rules.ts`. An error blocks conversion; a warning does not. The parser already reported problems it can only see in the raw cells (an unreadable date, a non-number in Rooms), so the CLI and API show both lists together.

`summarize(list)` counts what the planner and the hotel compare: guests, rooms, people, room nights, and the rooms needed on each night. A sharer adds people but no rooms.

## Design decisions
1. **One function per rule, all with the same shape.** Each rule takes a context and returns a list of issues. The context holds the entries, the block and a `report` helper. No rule can stop another, so one run shows the planner everything, and each rule can be tested on its own.
2. **Rows come from the parser, not from the entries.** The parser hands over `entryRows`, so messages can say "Row 7" (the row the planner sees in Excel) without changing what an entry looks like in JSON. A list built by hand still works: its messages say "Line 3".
3. **The name key ignores accents, case and punctuation.** "Müller" and "MULLER" match, so the duplicate-guest warning catches retyped names. The diff in M4 reuses the same key.
