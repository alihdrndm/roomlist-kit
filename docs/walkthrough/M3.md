# M3 walkthrough: export targets

## What was built
`exportRoomingList(list, targetId, options)` turns a validated list into the file a hotel's system imports. There are five targets: OPERA 5 (XML), OPERA Cloud (Excel), Maestro (CSV), and two of our own, canonical JSON and canonical CSV. It refuses to run, and says why, if the list has any error or the target is missing something it needs (for example Maestro needs the group reservation number and a first name on every guest). Guests are written primaries first, each followed by its sharers, and renumbered 1 to n, because the hotel's numbering is the output order, not the planner's own line numbers.

`listTargets()` returns every target with a list of facts: which ones were checked against the vendor's own documentation, and which ones are assumptions. `docs/ASSUMPTIONS.md` explains each assumption (A1 to A8), how to check it, and what to change.

## Design decisions
1. **Each target is a small object, not a class hierarchy.** It has an id, a file name, an options schema, a `preconditions` function and a `build` function. `export.ts` runs the same steps for all five (options, validation, required fields, preconditions, build), so a new hotel system means one new file plus one line in `registry.ts`.
2. **The two vendor golden files come from the spec, not from the code.** `we1.opera5.xml` and `we1.maestro.csv` were written by hand from the worked example; the exporters must reproduce those bytes. The canonical golden files are our own format, so they were generated once and checked by eye.
3. **Unknowns become options, not guesses.** OPERA 5's XML envelope, OPERA Cloud's date format and email type are all assumptions. They are options with defaults, so a planner whose hotel differs can change them without waiting for a code change.
