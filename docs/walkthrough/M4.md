# M4 walkthrough: comparing two rooming lists

## What was built
`diffRoomingLists(before, after)` answers the question a planner asks when version 2 of the list arrives: who is new, who is gone, and whose booking changed? It matches guests in two steps. First by confirmation number, because that is the hotel's own id for a booking: a corrected name ("Jonson" to "Johnson") still matches. Then by name, ignoring accents, case and punctuation. Whatever is left over was added or removed. For each matched pair it lists the fields that changed (dates, room type, counts, contact details, special requests, and who the guest shares a room with) as `before → after`. It also reports the change in room nights.

## Design decisions
1. **Line numbers are never used to match.** Planners renumber, insert and delete rows freely, so line 7 in v1 and line 7 in v2 can be different people. For the same reason, a sharer is compared by its primary's *name*, resolved inside each list on its own.
2. **Same-name guests are paired by arrival date.** Two "John Smith"s have the same name key, so the only thing that tells them apart is when they arrive. Each side is sorted by arrival, then line, and paired first with first. Changing one Smith's departure therefore can't swap him with the other.
3. **Matched entries are tracked per side.** Comparing a list with itself passes the same objects in twice. One shared "already matched" set would mark an entry used on both sides at once, so there are two sets.
